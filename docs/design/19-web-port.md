## 3. Determinism rules (the hard part)

1. **float32.** C# `float` is 32-bit. Wrap the result of **every** arithmetic operation in `Math.fround`, including intermediate ones. `a * b * c` is `fround(fround(a * b) * c)`. Every float literal (`0.05f`, `1.35f`, `2.2f`, `0.6f`, `90f`) is `fround(literal)`. Order of operations must match the C# source: the director rate is `base * (1f + Time / 90f * ramp) * mult * actMult`, evaluated left to right.
2. **Integers.** `uint` math uses `>>> 0` and `Math.imul`. `Rng.Next(n)` is `nextUInt() % n` on an unsigned value.
3. **Rounding.** C# `Math.Round(double)` is half-to-even. JS `Math.round` is not. Use `roundHalfEven` from the verifier.
4. **Time step.** `CombatSim.TickDelta = 0.05f`. `BattleSession.Tick(dt)` accumulates `dt` in a float and runs `while (pending >= TickDelta)`. With `dt = fround(0.05)` that is exactly one tick per call.
5. **Collections.**
   - `List<UnitState>` never shrinks; a dead slot is reused first-fit by `Spawn`. Index == unit id for events; `UnitState.Id` is a separate monotonically increasing counter.
   - `BoardModel` iterates a `HashSet<int>` (`_clearSet`) in `FinishClearStep` and `ClearRunsAndCreateSpecials`. .NET yields insertion order unless an element is removed and another added before the loop. In this code `Remove` happens after the last `Add`, so a JS `Set` (insertion order) is equivalent. The board fixtures would expose any deviation.
   - `Dictionary<int,...>` (`specialAt`, `hCells`) is iterated in insertion order (no removals).
6. **Constructors have side effects.** `new BoardModel(...)` runs `FillInitial` -> `EnsureMoves`, consuming RNG and possibly reshuffling; the events are discarded, the RNG advance is not. The initial grid in each board fixture proves this.
7. **Two RNG streams.** Board: `new Rng(seed)`. Combat: `new Rng(seed + 1)`. `Rng` takes an `int` and reinterprets as `uint`.
8. **Events are ordered.** `Events` is appended in exactly the order the C# code appends. Do not batch or sort.

## 4. Fixtures (`docs/web-port/fixtures/`, regenerated by Claude)

Produced by the real C# code via `NW.Editor.WebFixtureExporter.Export` (headless Unity). Two consecutive runs were byte-identical. Verify the reference helpers and the files themselves with:

```
node docs/web-port/verify-fixtures.mjs
```

That script is the executable spec for the Rng, the hash, `dailySeed`, `scoreTicks`, `sortKey`, Elo, tiers and the username key. It must print `OK`.

| File | What it pins down | Port is done when |
|---|---|---|
| `rng.json` | 9 seeds x (64 `NextUInt`, `Next(7)`, `Range(3,9)`, `Next01`) | `Rng` matches |
| `tables.json` | constants, unit catalog, per-level tables (board edge, gem colours, director mult, core HP, active lanes, troops, deploy options, enemy spawn tables, start resources), combo multipliers, shop boost multipliers | tables match |
| `formulas.json` | `dailySeed`, `sortKey`, `scoreTicks`, Elo, tiers, username keys (incl. Unicode edge cases) | helpers match |
| `combat_*.json` (17) | `CombatSim` alone: scripted spawns/strikes, every event, a state hash after **every** tick, full snapshots every N ticks | events + every hash match |
| `board_*.json` (21) | `BoardModel`: random playouts, handcrafted shapes (4/5-run, L/T), chains, special+special recipes, EMP, deadlock reshuffle, bad input | tape + hash after every swap match |
| `session_*.json` (3) | `BattleSession`: board swaps + deploys + combat together, with shop boosts in `level12_boosted` | step hashes match |

**Combat file.** `actions` are applied at tick `at` (after `at` ticks have run, before tick `at+1`) in listed order; `ret` is `Spawn`'s return. `events` rows are `[tick, phase, type, unit, target, amount, team, flag]`; phase 0 = emitted by an action, phase 1 = emitted during a tick. `hashEveryTickFrom1[i]` is the hash after tick `i+1`. Unit index in rows of `specIdx` refers to `tables.json` `catalogOrder`.

**Hash.** FNV-1a over 32-bit words: `h = 2166136261; for each word w: h = imul(h ^ w, 16777619) >>> 0`. A float contributes its float32 bit pattern. The exact word order for combat and board is `combatHashFromSnapshot` / `boardHashFromDump` in `verify-fixtures.mjs`. The combat hash includes private fields (`_directorBank`, `_nextId`), dead unit slots and their stale values, so a faithful translation (not a re-design) is required.

**Float text.** Floats are written with round-trip text. `Math.fround(Number(text))` recovers the exact value.

**Session files.** One frame = `session.Tick(0.05f)`. `inputs` lists swaps (with tapes) and deploys at their step. `combatEvents` use the same row format. The file records `usesGameDatabasePath: 0` (section 6.1) and the shop-boost multipliers applied.

**Debugging a mismatch.** Find the first tick/step whose hash differs, then compare against the nearest earlier snapshot. If that is not enough, ask Claude for a dense dump of that scenario around that tick. Do not change sim rules to make a fixture pass.

## 5. Corrections to older docs and comments

- `CombatSim` has **3 ground lanes + 1 air lane** (`GroundLanes = 3`, `AirLane = 3`). The header comment in `CombatSim.cs` ("five-lane", "4 ground lanes") and the wiki's "5 lanes" are stale. `Frontline` has 4 entries; index 3 (air) is never written.
- Boards are **square: 5x5 (levels 1-4), 6x6 (5-9), 7x7 (10-14), 8x8 (15-20)**. The wiki's "8-16 columns" is stale.
- `LevelConfig.ActiveGroundLanes`: 1 lane through level 3, 2 through level 7, 3 from level 8.
- `TooltipSystem.LaneTooltip` describes lanes 0-4; only 0-2 are ground and 3 is air.

## 6. Game-logic findings from building the fixtures (Claude owns the follow-up)

1. **`GameDatabase.asset` is dead and would be a trap.** `Assets/Resources/GameDatabase.asset` and the 12 `Data/Units/unit_*.asset` files have `m_Script: {fileID: 0}` (script reference lost), so `Resources.Load<GameDatabase>` returns null (confirmed: `tables.json` `gameDatabase.loaded = 0`). `BattleSession` therefore always takes the `UnitCatalog` fallback. The 12 database units are old prototype units (bomber, gunship, juggernaut, siege_tank...) with different stats. If the asset were ever repaired, the live game would silently switch to them. Web port: use `UnitCatalog` and ignore the database.
2. **Melee units are one-hit strikers against a core.** The core's defense zone (8 units, 50 damage per second) kills units that enter it. A trooper reaches `distToCore <= 2` with about 5 HP, lands one 10-damage hit, then dies. Snipers (range 25) shoot from outside the zone. Fixture `combat_melee_core_siege_and_defense.json` shows it. This is real behaviour, not necessarily a bug, but it is a balance fact for the design audit: at levels 1-2 (drone, trooper, turret only) the enemy core takes about 10 damage per trooper deployed.
3. **Daily-seed ghost replay uses the challenger's seed, not the ghost's.** `GhostRecord.seed` is recorded but the replay session is built with `DailySeed(level)` of the day the challenger plays. A ghost is a trace of deploy/strike events only, so the board differs from the one it was recorded on.
4. **Shop boosts change the sim.** `Deploy` multiplies `Damage` and `Speed` by `PlayerProgress.Active*Mult` (1.00, 1.05, 1.10, 1.20 by level). Fixtures pin boosts to 0 except `session_level12_boosted` (damage level 3, speed level 2).
5. **`NW_DEV`** is defined in the Android player settings (`NW_FIREBASE;NW_DEV`), which gives slot 2 everything unlocked. Strip it before a production build; the web build must not have it.

## 7. Firebase data model

Project id `neon-warfare` (Android package `com.zeusengine.neonwarfare`). The web app needs its own web-app registration in the Firebase console; its config object is public by design. Admin or service-account credentials must never be committed.

### 7.1 Existing wire formats (Android depends on these; do not change)

`leaderboards/{level}_{dailySeed}/entries/{pilotId}`: exactly these 11 fields (rules use `hasOnly`):

| Field | Type | Rule |
|---|---|---|
| `pilot` | string | <= 24 chars (usernames are 3-16) |
| `pilotId` | string | must equal the doc id; Android uses a random 32-hex GUID per save slot |
| `mmr` | int | |
| `result` | int | 0 loss, 1 win |
| `durationTicks` | int | 0 <= x < 1e9 |
| `scoreTicks` | int | 0 <= x < 1e9; **must be >= 1** or the score check fails |
| `speed` | number | |
| `recordedUtc` | int64 | .NET `DateTime.ToBinary()`; no rule check (section 9) |
| `score` | int | `result*1e9 + (result==1 ? 1e9 - scoreTicks : scoreTicks)` |
| `ghost` | string | JSON text, size < 60000 **characters** |
| `updatedAt` | timestamp | server timestamp |

Write only when the new run beats the incumbent (`RankLadder.Beats`); the write is a full overwrite. Board key: `dailySeed(level)` from the UTC date the match **started**. `scoreTicks = max(1, roundHalfEven(durationTicks / speed))`, with `speed <= 0.05 -> 1`.

`usernames/{key}`: fields `pilotId`, `uid`, `name` (3-16), `claimedAt`. `key` = `usernameKey(name)` (letters/digits/`_`/`-`, whitespace collapsed to `_`, lowercased). Create requires `uid == auth.uid`; update/delete only by the owner.

`diagnostics/{id}`: write-only crash reports (Android). The web client may add its own sink later; do not widen this block.

Ghost JSON (`GhostRecord`): `version`(1), `id`, `pilot`, `pilotId`, `mmr`, `level`, `theme`, `seed`, `gemCount`, `difficulty`(float), `result`, `durationTicks`, `scoreTicks`, `speed`, `recordedUtc`, `bundled`, `actions[]` of `{tick, type, unit, lane, amount}` where `type` 0 Deploy, 1 Laser, 2 Orbital, 3 Emp, 4 Shockwave. Only player deploys and board-to-war strikes are recorded; a ghost with no actions is not stored.

### 7.2 Accounts (web)

Player-facing: username + password. Firebase Auth only knows email + password, so:

1. First load: anonymous sign-in. The player can play immediately.
2. "Create profile": normalise the username with `normalizeUsername`, require `usernameValid`, compute `key = usernameKey(name)`.
3. Claim `usernames/{key}` **in a transaction** (read; if it exists with another uid, report "taken"; otherwise create). Treat a permission-denied on create as "taken".
4. Convert the anonymous account with `linkWithCredential(EmailAuthProvider.credential(email, password))`, where `email = 'u' + sha256hex(key).slice(0, 40) + '@players.<chosen-domain>'` (ASCII-safe and within local-part limits for any Unicode name). Verify Firebase accepts the domain you choose. If linking fails, delete the claim.
5. "Sign in": same derivation, `signInWithEmailAndPassword`. The cloud profile wins over any anonymous local progress unless the player confirms otherwise.
6. Password: at least 8 characters. There is no recovery without a real email: say so in the UI; offer an optional recovery email later.

### 7.3 Saves (new)

Mirror of `PlayerProgress` (currently Android `PlayerPrefs`). Per slot `s` in 0..2: `currency` (5 ints, cap 9999), `unlocked` (level ints), `name` (default `PILOT n`), `pilotId` (32-hex GUID, minted on slot creation and on delete), `usernameKey`, `renames`. Global: `mmr` (1200), `tokens`, `boostDmg`/`boostSpd` (0..3), `cosmetics` (owned ids per category), equipped cosmetic/skin settings, `history` (<= 30 match outcomes). Proposed paths and rules: `docs/web-port/firestore.rules.proposed`. Mirror to local storage so the game works offline; sync on sign-in and after each match.

## 9. Unverified or open

- **Rules syntax is unvalidated** (no emulator run here). Test in the console Rules Playground or the emulator before publishing.
- **`recordedUtc`** is an int64 around 4.6e18, above JavaScript's safe-integer range. How the Firestore web SDK stores a large number, and whether Android's `GetValue<long>` then reads it, is untested. Until resolved the web client should write `0` (Android's `SetAt` treats 0 as "unknown"); tie-breaks by time then fall back to equal.
- **Leaderboard writes are not tied to the caller.** Any signed-in user can overwrite any `pilotId` entry (pre-existing, also true on Android). Closing it needs an Android update first (stage 2 in the proposed rules file).
- **Google sign-in inside the itch.io iframe** is untested and likely to fail; the plan avoids it (email/password).
- The Cloud Function that re-simulates a ghost server-side does not exist yet; it needs the TypeScript sim plus Firebase's pay-as-you-go plan.
- `docs/design/18-leaderboard-firebase.md` (composite index and rules copy) was not cross-checked against the deployed console rules.
